# Action Latency Microbenchmarks

This runner measures executor-facing transition action latency on the real cluster.
It bypasses the planner and creates minimal `MigActionPlan` objects directly, so the
results capture executor, node-agent, router, runtime, Kubernetes, and GPU behavior
without mixing in Stage1/Stage2/Stage3 planning time.

## What It Measures

MIG configuration primitives:

- `create_mig(profile)`: clean GPU to one MIG instance of `1g`, `2g`, `3g`, `4g`, or `7g`.
- `create_mig_ready(profile)`: `create_mig` plus `register_mig_devices`, including resource visibility wait.
- `delete_mig(profile)`: one MIG instance to empty GPU.
- `configure_full_template(template)`: clean GPU to a full A100 template.
- `configure_full_template_ready(template)`: full template configuration plus `register_mig_devices`.
- `clear_template(template)`: populated template to empty GPU.
- `partial_reconfig(source_template -> target_template)`: every supported partial patch generated by the current Stage3 partial-reconfig rules.
- `partial_reconfig_ready(source_template -> target_template)`: partial patch plus `register_mig_devices`.

Serving instance primitives:

- `create_instance(workload, profile)`: create MIG slot, create runtime pod, wait for health/CUDA binding, and activate route.
- `delete_instance(workload, profile)`: deactivate route, wait drain, and delete runtime pod.
- `route_activate(workload, profile)`: runtime already exists; measure activation only.
- `route_deactivate_drain(workload, profile)`: endpoint already active; measure stop-new-requests plus drain.
- `migrate_container`: use `create_serving_instance + route_deactivate_drain_total + delete_instance` when replaying Jormungandr primitives in simulation.
- `repartition_gpu`: use `partial_reconfig_ready` when partial patch is possible, otherwise `configure_full_template_ready`.

Workloads/request classes:

- `resnet50`
- `vgg16`
- `vit_base`
- `gpt2_p64_o64`
- `gpt2_p512_o512`
- `llama_p1024_o128`
- `llama_p2048_o64`
- `llama_p4096_o512`

The route key is the full request class, for example `gpt2_p64_o64`, while the runtime image/model family can still be `gpt2` or `llama`.

## Outputs

Each run writes under:

```bash
eval/action_latency_microbench/results/$RUN/
```

Files:

- `action_latency_matrix.csv`: all planned cases before execution.
- `action_latency_matrix.json`: same matrix in JSON.
- `action_latency_microbench.csv`: one row per observed executor action status, plus composite rows such as `create_serving_instance`.
- `action_latency_summary.csv`: grouped median, p95, mean, and stddev.

## One-Command Runs

Matrix-only dry run. This does not mutate the cluster:

```bash
RUN=action-latency-matrix-$(date +%Y%m%d-%H%M%S)
python3 eval/action_latency_microbench/run_action_latency_microbench.py \
  --suite all \
  --trials 20 \
  --llm-trials 5 \
  --run-id "$RUN"
```

Small cluster smoke test. This mutates one available GPU:

```bash
RUN=action-latency-smoke-$(date +%Y%m%d-%H%M%S)
python3 eval/action_latency_microbench/run_action_latency_microbench.py \
  --namespace or-sim-exp \
  --execute \
  --suite mig-only \
  --trials 1 \
  --max-partial-cases 3 \
  --run-id "$RUN"
```

Full recommended benchmark:

```bash
RUN=action-latency-$(date +%Y%m%d-%H%M%S)
python3 eval/action_latency_microbench/run_action_latency_microbench.py \
  --namespace or-sim-exp \
  --execute \
  --suite all \
  --trials 20 \
  --llm-trials 5 \
  --run-id "$RUN"
```

Fast one-hour calibration benchmark. Run the three commands in three terminals:

```bash
RUN=action-latency-fast-$(date +%Y%m%d-%H%M%S)

python3 eval/action_latency_microbench/run_action_latency_microbench.py \
  --namespace or-sim-exp \
  --execute \
  --suite all \
  --trials 3 \
  --llm-trials 2 \
  --max-partial-cases 18 \
  --instance-profiles 1g,3g,7g \
  --physical-gpu ampere-gpu0 \
  --shard-count 3 \
  --shard-index 0 \
  --run-id "$RUN-ampere-gpu0"

python3 eval/action_latency_microbench/run_action_latency_microbench.py \
  --namespace or-sim-exp \
  --execute \
  --suite all \
  --trials 3 \
  --llm-trials 2 \
  --max-partial-cases 18 \
  --instance-profiles 1g,3g,7g \
  --physical-gpu ampere-gpu1 \
  --shard-count 3 \
  --shard-index 1 \
  --run-id "$RUN-ampere-gpu1"

python3 eval/action_latency_microbench/run_action_latency_microbench.py \
  --namespace or-sim-exp \
  --execute \
  --suite all \
  --trials 3 \
  --llm-trials 2 \
  --max-partial-cases 18 \
  --instance-profiles 1g,3g,7g \

  --shard-count 3 \
```

```bash
RUN=action-latency-ampere-gpu0-$(date +%Y%m%d-%H%M%S)
python3 eval/action_latency_microbench/run_action_latency_microbench.py \
  --namespace or-sim-exp \

  --trials 20 \
  --llm-trials 5 \
  --physical-gpu ampere-gpu0 \
  --run-id "$RUN"
```

## Preconditions

The selected GPU should be empty/available before the run. The runner also performs cleanup before and after each trial, but starting from a clean cluster makes failures easier to interpret.

Use the baked/warmed runtime images for formal measurements. Otherwise LLM create latency will include image pull or cold model cache effects.
