### 2.1 Stage 3 partial reconfiguration 的规则

对一块 GPU 做 partial 时，每个 workload 需满足：source 删掉这块 GPU 上要删的实例后剩下的容量，加上能在这些删除之前就绪的新容量，不低于承诺 min(旧需求, 新需求)。能在删除之前就绪的新容量包括：

- 其他 GPU 上新建的实例，以及保留实例改 batch 带来的 μ 增量；
- 本 GPU 上只算保留 slot（换进来的 workload 或 batch 增量）。本 GPU 新建的 MIG 实例由删除之后的 `configure_partial_profile` 创建，不计入。

执行时的安全由 capacity 依赖边保证：每个减少容量的动作都要等足够的新副本就绪。在这组 E1 上，12 轮都没有借 GPU（R5、R12 走 partial），对所有可能执行顺序做容量审计，SliceWise 为 0 违规。与 eval 的差异见 `docs/stage3-partial-capcheck-notes-20260930.md`。

## 3. 发流器

`live_traffic_20260926.py` 中的 `ContinuousRateSender` 和 `BoundedAsyncSender`，由 `live_runner_20260926.py` 驱动。

- **开环、一个请求一张图。** 发流器模拟上游用户：每个请求是一张图（vision）或一个 prompt（LLM），到点就发，不等上一个请求完成。凑批由 router 负责，发流器不打包。
- **Poisson 到达**（`--arrivals poisson`）。到达间隔服从均值 1/d 的指数分布。每次切换速率时，每个 workload 的随机数生成器用 (seed=71, workload, 轮次, 窗口) 的哈希重新初始化。所以 SliceWise 和 SW−C 在同一轮、同一窗口里收到完全相同的到达间隔序列。离线验证：设定 400/s 时实测 401.0/s，到达间隔变异系数 0.989（指数分布的理论值为 1），两个实例生成的序列相同。
- **每轮的速率切换**：
  1. 这一轮的 plan 生成并审计通过后，切换到承诺速率 min(旧需求, 新需求)，然后批准 plan；
  2. executor 报告 plan 完成后，切换到新需求，停留 30 s（dwell）；
  3. 然后规划下一轮。R12 之后发流停止，R13 把集群清空。
- **发送端上限**：每个 workload 最多 256 个未完成的请求，总共最多 1024 个。超过时新请求不发出，记为 `rejected_pending_bound`（下文称"过载"）。不重试。
- 每秒调用一次 `gc.freeze()`，避免大量请求记录触发全量 GC，使发送卡顿。最大发送间隔约 0.13–0.19 s。
- 每个请求记录它被调度时所在的轮次和窗口（`transition` / `steady`），在途请求保持原来的标记。

## 4. Router

`cmd/runtime-router/main.go`。router 是上游的一个简易替身：它自己的开销（往返、凑批等待）由它自己负责，不计入 catalog。

- **vision：按副本拉取式凑批。** 每个副本前有一个队列。副本能接下一批时，router 从队列里取最多 batch size 个请求，作为一次调用发给 runtime。
  - 每个副本最多同时有 `VISION_PIPELINE_DEPTH = 2` 批在飞：当前批在 GPU 上计算时，下一批已经在 runtime 里排队，router ↔ runtime 的往返（约 1–2 ms）与 GPU 计算重叠。
  - 第二批只在凑满时才发，不会把一批拆成两半。副本空闲时，最多等 `VISION_MAX_BATCH_WAIT = 5 ms` 就发出不满的批。
  - runtime 收到结果后立即释放槽位、派发下一批，响应交回客户端放在之后做（a1444de）。之前交回响应会占着槽位，并与请求到达、`/routes` 查询争同一把锁，vgg16 2g b4 因此只跑到容量的 0.78。
- **LLM：每个副本一次一个请求**（`ENDPOINT_MAX_CONCURRENCY = 1`），与 profile 条件一致。
- **选副本**：在该 workload 的就绪副本里，选 (在飞请求 + 队列中请求) / 容量权重 最小的一个。权重取路由的 capacity，也就是 catalog μ。
- **路由变更**：executor 通过 `/routes` 的 patch 原子地改变单个副本的 active、acceptingNew、draining、batchSize。去激活的副本不再接新请求，队列中的请求改派给其他副本。
- **route GC**：每 30 s 检查一次各副本的 `/healthz`，超时 3 s，连续 3 次失败才删除路由。runtime 的 `/healthz` 由 HTTP 进程用缓存的快照回答，不排在推理后面。最终两组 run 里没有发生 route GC。

## 5. 分析方法

脚本：`e1_analyze.py`（`makespan_window_metrics.csv` 等）、`s46_analyze.py`、`e1_capacity_factor.py`。

### 5.1 窗口

- **makespan 窗口**：这一轮 plan 的第一个动作开始，到最后一个动作结束。这是集群真正在变化的时间。
- 发流器切到承诺速率的时刻比这更早：plan 批准时就切了，中间隔着 planner 求解、审计和 executor 启动，约 8–14 s，这段时间集群没有变化。所以指标只统计 makespan 窗口里发出的请求，不统计整个 `transition` 窗口。
- **稳态窗口**：变换完成后的 30 s dwell，作为基线。

### 5.2 每个请求的分类

makespan 窗口里发出的每个请求，恰好属于下列一类，分母统一是发出的请求数：

| 类别 | 条件 |
|---|---|
| 按时 | 完成，且端到端延迟 ≤ SLO + router 固有延迟 |
| 超时 | 完成，但端到端延迟 > SLO + router 固有延迟 |
| 断流失败 | HTTP 404：该 workload 没有就绪副本 |
| 过载失败 | 发送端上限（积压超过 256） |

**两种 SLO 口径**

- **profile 口径**：runtime 报告的计算时间是否超过 catalog SLO。这正是 planner 选择选项时的检查，只对完成的请求有意义。
- **SLO + router 固有延迟**：catalog 的 SLO 限制的是一批的计算时间。请求在 router 里还有一段与容量无关、总是存在的等待，把它加到阈值上，超出的部分才是积压（容量不足）造成的额外延迟：
  - vision：阈值 = SLO + (b − 1)/λ + t_batch + 2 ms。其中 (b − 1)/λ 是一批里第一个请求等待其余 b − 1 个的时间，λ 为该副本在窗口内的完成速率；t_batch 是两批流水线中排在前面那一批的计算时间，取该副本的中位数；2 ms 是往返。
  - LLM：TTFT ≤ TTFT SLO + 2 ms，且 TPOT ≤ TPOT SLO。

SLO：resnet 100 ms，vgg16 100 ms，vit 300 ms；gpt2_p64 TTFT 50 / TPOT 20 ms，gpt2_p512 100 / 20，llama_p1024 180 / 35，llama_p2048 250 / 35。

### 5.3 实际流量

对 vision 的每一轮：承诺速率、makespan 窗口内实际发出的速率、在窗口内完成的速率，以及完成 / 承诺。

## 7. 实际容量、容量校准与 μ 系数

### 7.1 系数的定义与计算

系数 = 副本的实际容量 / 该副本选项的 catalog μ。catalog μ 按"workload × MIG profile × batch"查 catalog v3：profile 来自 runtime id 的最后一段，batch 取副本配置的 `maxBatchSize`。实际容量只有在副本饱和时才能测到。饱和时副本的队列里一直有请求，每处理完一批就马上接下一批，它的完成速率就等于它的最大处理能力；不饱和时，完成速率只反映分到它的负载。

系数有两个来源，发流方式和饱和的判断方式不同。

**(a) E1 run 中的系数**（`e1_capacity_factor.py <run> catalog_newest_v3.csv`）

用的就是 E1 本身的发流器：Poisson 到达，按需求速率发送（第 3 节），不额外加压。只有规划余量薄、实际容量追不上需求的副本才会饱和，所以只能测到少数副本。

1. 按 router 派发时刻（`routerDispatchAt`）把请求分到每一秒。某一秒对某个 workload 算作**饱和**，要同时满足：
   - 这一秒派发的请求，router 排队时间（`queueWaitMs`）的中位数 > 50 ms；
   - 其中 ≥ 95% 是以满批发出的。这一条用来排除大 batch 的凑批等待：vit b16 每个副本每秒约 61 个请求，凑满一批要约 260 ms，排队时间很长，但批常常凑不满，说明副本其实跟得上。
2. 只保留前后一秒也饱和的秒，去掉每段连续饱和的首尾秒，因为这两秒可能只饱和了一部分。
3. 对每个"副本 × 轮次"：实际容量 = 在这些饱和秒里完成的请求数 / 饱和秒数。饱和秒少于 5 的不计。
4. 系数 = 实际容量 / catalog μ，再按窗口（makespan / 稳态）、主机、选项汇总。

**(b) 容量校准中的系数**（`e1_capacity_calibration.py`，结果在 `cluster_results/20260930T112125Z-capacity-calibration/`）

用了**另一种发流方式**，目的是让所有副本同时饱和，覆盖 E1 里测不到的副本（rtx1 上的副本、resnet、LLM）：

1. 依次部署 E1 的 R1–R12 布局，用与 E1 相同的变换，变换期间不发流。
2. 每个布局就绪后，从 router 的 `/routes` 读出每个 workload 已放置副本的 catalog 容量之和 C_w。所有 workload **同时**以 **1.3 × C_w 的固定间隔**（`ContinuousRateSender`，arrivals=fixed）发流 45 s。发送端上限和 E1 相同（每个 workload 256），积压超出上限后被拒绝是预期的，这保证队列一直是满的。
3. 丢掉前 10 s（预热、积压建立），在 [10 s, 45 s) 内：
   - vision 副本：实际容量 = 完成请求数 / 35 s，并记录满批比例，只统计满批 ≥ 95% 的副本；
   - LLM 副本（一次一个请求）：实际容量 = 1 / 相邻完成时间间隔的中位数（35 s 里只有几到几十个请求，用中位数更稳）。
4. 系数 = 实际容量 / catalog μ，按主机和 vision / LLM 汇总。

这种发流方式让整块 GPU 的所有切片同时满载，比 E1 更忙，所以测出的是最坏情况。它只用来测容量，不用来评估 SliceWise：超载时任何系统都兑现不了承诺。

### 7.2 结果

(a) E1 run（只统计满批饱和的秒）：

| 来源 | 样本（副本 × 轮次） | 最低 | 中位数 | 最高 |
|---|---|---|---|---|

- fast3 两组的中位数（0.958–0.960）与 fast2 时一致（0.956–0.957），μ 仍取 0.93，不需要重做实验。
- 迁移窗口里的系数更低。最低的几个都在 ampere-gpu1 上，当时同一块 GPU 上有 5 个新副本在激活（加载、预热），或者副本自己正在改 batch。

### 7.3 同卡功耗降频（DCGM 采样）

- E1 的 R1 期间，ampere GPU0 的功耗中位数为 253 W（上限 250 W），SM 频率最低 1365 MHz（满速 1410 MHz）。
- R8–R9 期间，ampere-gpu1 为 251–253 W，SM 频率降到 1305–1350 MHz，vit b16 每批 261–265 ms。
- MIG 隔离 SM 和显存，但功耗和频率是整卡共享的：同卡切片都忙时，所有切片一起变慢。profile 时一块 GPU 上只有一个切片，测不到这种情况。

### 7.4 ampere 的 CPU 频率（turbostat 采样）

- ampere（Dell R750xa）没有 cpufreq 驱动，频率由硬件按负载自己调节。
- resnet 1g b1 一次计算约 4.8 ms，主要受 CPU 下发 kernel 的速度限制。推理核高于 2 GHz 时每个请求 4.80 ms；在 1.2–2.0 GHz 时是 6.5 ms，慢 35%。
- 推理子进程改成忙等（fast3）之后，推理核不再进入 C6（C6 占比为 0），R4–R6 的频率有提高；但 R7–R11 该核仍在约 1.9 GHz，resnet 仍为约 6.4 ms。同一时间其他忙碌的推理核平均能到 2.6–3.1 GHz，原因未查明。
- 这是最终 SliceWise 中 resnet 在变换期间超时 11% 的原因，作为已知局限记录。

### 7.5 μ 系数

- **推荐 μ = 0.93**，规划时使用 catalog × 0.93。依据是 (a)：它覆盖稳态中位数 0.957 和迁移窗口中位数 0.942，fast3 两组 run 重算后的结果一致，但不覆盖同卡多个副本同时激活时十几秒的低谷（0.86），也不覆盖 7.4 节的 CPU 频率问题。
- **离线可行性**（`headroom_offline_sweep.py`，把需求除以系数）：
  - catalog × 0.93 或 × 0.88 时，R1 需要超过 3 块 GPU。R1 最多承受 0.975，也就是约 2.6% 的余量。
  - R2–R12 在 0.93 下全部可行，R5、R12 多用一块 GPU。
- **μ 实验**（`--e1-first-round 2`，只跑 SliceWise，catalog × 0.93，跳过 R1）：R2–R5 正常，R6 失败。乘了 0.93 之后，planner 第一次在 R6 安排了临时副本（rtx1 上的 resnet 2g），executor 部署它时报 `target runtime not found`：临时副本不在交给 executor 的目标 runtime 列表里。之前所有 E1 都没有用到临时副本。这个缺口还没修，μ 实验没有完成，run 目录没有提交。

## 8. 已知局限

1. **ampere 上受 CPU 下发限制的小 batch 选项**（resnet 1g b1）在部分负载下因 CPU 频率低而慢 20–35%（7.4 节）。
2. **同卡功耗降频**：同一 A100 的切片都忙时，SM 频率下降 3–7.5%，所有切片一起变慢（7.3 节）。
3. **catalog 在 E1 里偏乐观约 4–5%**（中位数 0.95–0.96）。规划余量薄于这个差距的轮次会出现稳态积压，例如 vgg16 R5–R7、vit R8–R9。推荐的 μ 系数用来补偿这一点，但 μ 实验因为临时副本的问题没有跑完。
4. **稳态 SLO 违反偏高**：planner 按单批计算时间判断 SLO，没有考虑 router 的凑批等待和流水线排队。vit b16、vgg16 b16 的端到端延迟在稳态就超过 catalog SLO，因此 SLO 违反按 SLO + router 固有延迟判断（5.2 节）。
5. **LLM 样本太少**：makespan 窗口里每个 LLM workload 只有约 10 个请求。LLM 一次处理一个请求，Poisson 到达时排在正在生成的请求后面，TTFT 就会超过 SLO。
