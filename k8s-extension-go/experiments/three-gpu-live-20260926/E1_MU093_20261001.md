# E1 μ = 0.93 实验与分析（2026-10-01）

本文记录 μ 系数实验：规划时把 catalog 乘以 μ = 0.93，其余与最终 E1 相同，只跑 SliceWise。μ 的定义和取值依据见 `E1_FINAL_20260930.md` 第 7 节；对照组是最终 SliceWise run `20260930T154846.076040Z`（下文称"不乘 μ"）。

## 1. 设置

| 项 | 取值 |
|---|---|
| run 目录 | `cluster_results/20260930T172233.426344Z` |
| catalog | `catalog_newest_v3_mu093.csv`（catalog v3 的 μ × 0.93，其余列不变） |
| planner-engine | `mu093-20260930`：代码与 `refined-20260930`（c88323b）相同，镜像内的 catalog × 0.93 |
| transition-executor | `temp2-20261001`（37615f0，第 2 节） |
| 其余组件 | 与最终 E1 相同：router `early-20260930`、node-agent `join-20260930`、runtime `*-fast3-20260930`、planner-controller `headroom-20260929` |
| 规划参数 | `conservative3gMu = true`，`capacityHeadroom = 0`，GPU 预算 3 |
| 发流 | Poisson（`--arrivals poisson`），与最终 E1 相同 |
| 轮次 | R2–R12，跳过 R1 |

```
python3 live_runner_20260926.py --execute --e1 --e1-first-round 2 \
  --catalog catalog_newest_v3_mu093.csv --conservative-3g-mu --arrivals poisson \
  --router-url http://115.145.179.144:10680
```

- **R1 跳过**：乘 0.93 后 R1 需要超过 3 块 GPU。离线扫描显示 R1 最多只能承受 0.975，这本身就是乘 μ 的一个结果。
- **R2 是初始放置**：从空集群建出 R2 布局，变换期间没有流量（source 承诺为 0），和不乘 μ 时的 R1 一样，不计入变换统计。
- 没有引入新的规划参数，μ 只作用于 catalog。

## 2. 为跑通 μ 实验做的修复

乘 μ 之后，planner 第一次在 E1 里用到 Stage 3 的临时容量（R6：借 rtx1，放一个 resnet 2g 临时副本，再对 ampere-gpu1 做 partial）。之前所有 E1 都没有走到这条路径，暴露了 executor 的两个问题：

| # | 现象 | 原因 | 修复 |
|---|---|---|---|
| 1 | R6 部署临时副本时报 `target runtime not found`（run `163828`） | planner 把临时副本列在 `summary.executionRuntimes`，executor 执行动作时只查 `desiredRuntimes`（目标状态） | 4093edb：执行动作时查目标 runtime，再加上只在 `executionRuntimes` 里的 runtime。hostPort 由 GPU 和 slot 固定算出，两份列表合并不会冲突。最终状态验证仍只对照目标 |
| 2 | R6 执行成功，但 R7 前的 preflight 发现 registry 不稳定（run `170311`） | plan 结束时 `persistFinalLogicalBindings` 按 `physical_id_map` 写 logical-binding ledger，而这个 map 也包含已经归还的借用 GPU（logical 1001 → rtx1），于是 rtx1 被记为 active 但没有 runtime | 37615f0：只为目标状态中的 GPU 写 binding。对 9/30 的 260 个 plan 回放，只有两个借了 rtx1 的 R6 plan 受影响 |
| 3 | 实验跑完，但 runner 的输出验证报 "round 3/5 has incomplete actions" | R3、R5 是 0 个动作的轮次（第 3.1 节），验证要求每轮都有 action status | runner 只在 plan 有动作时要求 action status；`e1_analyze.py` 把 0 动作的轮次写进 `makespan_window_metrics.csv`（`no_op = True`，窗口 0 s，违反率 0）。重跑验证无错误，见 `analysis/revalidation_20261001.json` |

- 两次失败后，集群都停在 R6 的状态，registry 要求修复 rtx1。每次都手动提交了一个修复 MigActionPlan（只对 rtx1：清 binding → 清 template → 归还 GPU），再清到空后重跑。
- 失败的 run `163828`、`170311` 没有提交。
- `audit_makespan_run.py --expected-rounds 11`：通过，0 错误。

### 3.3 改善从哪里来

不乘 μ 时，晚到集中在少数几轮，它们都是实际容量低于承诺、副本饱和的轮次（晚到 / 完成）：

| workload | 窗口 | 集中的轮次 | 原因 |
|---|---|---|---|
| resnet | makespan | R4：2442 / 5883（占 R3–R12 该窗口 resnet 晚到的 95%） | R4 中 ampere-gpu0 (6,7) 从 b4 改成 b1，1g b1 副本饱和，容量系数 0.847 |
| vgg16 | makespan | R3 1444 / 7004，R5 1733 / 15735，R6 510 / 510 | vgg16 2g b16 系数 0.955–0.965，余量不够，积压延续进下一轮 |
| vgg16 | 稳态 | R5 13842 / 13842，R6 7983 / 13810，R7 13890 / 13890 | 同上，稳态积压；R5–R7 的 405 个失败也来自这里 |
| vit | makespan | R3 1554 / 1731，R9 1812 / 2894 | vit 1g b16 饱和（R9 队列等待中位数 0.44–0.96 s，全是满批，系数 0.93–0.97） |
| vit | 稳态 | R5 3657 / 3704，R8 1399 / 3730，R9 3351 / 3669 | 同上 |

不饱和的轮次里，vit b16 即使每批要凑约 260 ms，晚到也是 0（例如 R4、R5、R10–R12 的 makespan 窗口）。所以晚到的减少**不是因为 batch 变小**，而是因为：

1. **容量余量**：承诺容量按 catalog × 0.93 计算，实际容量的中位数（catalog 的 0.95–0.96）被覆盖，上表这些"实际低于承诺"的轮次在 μ run 里基本消失：vgg16 稳态最多 2311 / 9518（R8），vit 稳态最多 562 / 3621（R7），没有失败。系数的低值（resnet 1g b1 0.85、vgg16 2g b32 0.92、第 3.5 节的 ampere b1 0.87–0.89）仍不被 0.93 覆盖。
2. **轮次本身变了**：R3、R5 变成 0 动作，R4 的 makespan 从 35.8 s 缩到 6.0 s。不乘 μ 时晚到最多的两个 makespan 窗口（R3、R4）在 μ run 里没有或很短。

planner 选的选项也变了（按服务的请求数统计，R3–R12）。这是同样的需求除以更小的 μ 之后 Stage 1 的选择结果，上面的数据没有显示它对晚到有单独的影响：

|---|---|---|
| resnet50 | 1g b1 80%，1g b4 20% | 1g b1 79%，2g b1 21% |
| vgg16 | 2g b16 57%，2g b4 18%，2g b32 14%，2g b1 10% | 3g b4 65%，2g b32 12%，2g b16 12%，3g b1 6%，4g b1 3%，2g b1 2% |
| vit_base | 1g b16 74%，1g b1 26% | 2g b1 76%，1g b1 24% |

### 3.4 代价

- R1 在 3 块 GPU 内不可行。
- R6 要借 rtx1 部署临时副本，makespan 46.5 s；R5、R12 的目标布局各多用一块 GPU。
- makespan 合计反而更短（160.9 s vs 183.7 s），主要是 R3、R5 不需要变换，R4 从 35.8 s 缩到 6.0 s。

## 4. ampere 上的 b1 受 CPU 频率限制

### 4.1 现象

同一个选项、同一个 MIG profile，ampere 上的 resnet b1 副本有两种速度：接近 profile，或者慢 35–45%。两种状态之间是跳变，不是逐渐变慢。

每个副本每轮 GPU 计算时间（`runtimeLatencyMs`）的中位数，与 profile 的 GPU 计算时间（该 GPU 上 `1000 / compute_mu`）比较：

|---|---|---|---|---|---|
| 不乘 μ | resnet ampere-gpu0 1g (6,7) | R4–R6 | 4.75–5.05 ms | 4.69 ms | 1.01–1.08 |
| | | **R7–R11** | **6.32–6.39 ms** | 4.69 ms | **1.35–1.36** |
| | | R12 | 4.97 ms | 4.69 ms | 1.06 |
| μ = 0.93 | resnet ampere-gpu0 1g (2,3) | R2–R4 | 4.86–4.94 ms | 4.69 ms | 1.04–1.05 |
| | | **R5–R6** | **6.55–6.66 ms** | 4.69 ms | **1.40–1.42** |
| | resnet ampere-gpu1 2g (0,2) | R2–R4 | 4.15–4.34 ms | 4.26 ms | 0.97–1.02 |
| | | **R5–R6** | **6.01–6.16 ms** | 4.26 ms | **1.41–1.45** |

| | resnet rtx1 2g (0,2)（临时副本） | R6 | 4.68 ms | 4.62 ms | 1.01 |

| | vit ampere-gpu1 2g (2,4) | R7–R9 | 11.43–11.54 ms | 10.75 ms | 1.06–1.07 |

- **受影响最大的是 resnet b1**：一次计算不到 5 ms，大部分时间花在 CPU 下发 kernel 上，推理进程所在 CPU 核的频率直接决定它的速度。慢状态下是 6.0–6.7 ms，比 profile 慢 35–45%。R10–R12 的 (6,7) 副本在一轮之内就在两种状态之间来回切换：快 4.7 ms，慢 6.4 ms，没有中间值。
- **vit b1、vgg16 3g b1 慢 6–8%**，出现在 ampere-gpu1 上同卡多个切片都忙的轮次（R7–R9）。vit b1 约 20 ms，是计算密集的，这个幅度和同卡功耗降频一致（`E1_FINAL_20260930.md` 第 7.3 节：ampere-gpu1 到 250 W 上限时 SM 频率降低 4–7.5%）。本次 run 没有做 DCGM 采样，不能确定是哪一种原因。
- vit b1 除了 GPU 时间变长，请求之间的间隔也变长了。ampere-gpu1 1g (0,1) 在 R9 饱和时每秒完成 44.3 个，即每个请求 22.6 ms，其中 GPU 计算 21.2 ms，间隔约 1.4 ms。profile 时这个间隔只有约 0.19 ms（wall 19.99 ms vs compute 19.80 ms）。这部分是 CPU 侧的开销（HTTP / 进程间通信 / 下发），同样受核频率影响。
- rtx1 上只有一个 b1 视觉副本（R6 的临时 resnet 2g，1446 个请求），它和 profile 一致。样本很少，只能说明这一次没有出现慢状态。

### 4.2 CPU 频率的证据（turbostat，最终 run 期间采样）

- ampere（Dell R750xa）没有加载 cpufreq 驱动，频率由硬件按负载自己调节，操作系统设不了。基准频率 2.0 GHz。
- 最终 SliceWise run（154846，fast3 runtime）期间用 turbostat 逐秒采样。resnet 1g (6,7) 副本的推理核是 CPU 14（与超线程 70 共用一个物理核）：
  - R4–R6：该核忙碌时频率 2.65–2.76 GHz，resnet 4.8–5.05 ms；
  - R7–R11：该核只有 1.87–1.98 GHz，resnet 6.3–6.4 ms；
  - 同一时间，其他忙碌的 runtime 推理核平均 2.6–3.1 GHz。所以不是整颗 CPU 降了频，而是这一个核被压低了。
- fast2 runtime（推理子进程阻塞等待）的 run 中，核 14 在 R7–R11 为 1.72–1.97 GHz。改成忙等（fast3）之后，C6 占比降为 0，R4–R6 的频率提高了，但 R7–R11 仍在约 1.9 GHz。所以**忙等消除了 C6 唤醒延迟，但没有解决频率问题**。
- 原因推测（**未验证**）：每个 runtime 分到一个物理核的两个超线程（例如 14 和 70），而推理子进程是单线程的，可能在两个超线程之间来回迁移。每个逻辑 CPU 看上去都只有 50–70% 忙碌，硬件按逻辑 CPU 的利用率决定频率，于是不给满速。
- 本次 μ run 没有做 turbostat 采样。4.1 节里慢状态的出现时间和幅度与最终 run 一致，但没有逐秒的频率数据直接对应。

### 4.3 与 catalog 的关系

- catalog v3 在每块 GPU 上单独 profile，测量时主机上只有这一个 runtime，推理核能跑到 2 GHz 以上。ampere 上 resnet 1g b1 测到 204.8–206.6 个/s（wall，4.84–4.88 ms；GPU 计算 4.68–4.69 ms）。
- catalog 取三块 GPU 中最慢的一块，resnet 1g b1 的 catalog μ 是 rtx1 的 190.19 个/s（5.26 ms），μ 缩放后是 176.88 个/s（5.65 ms）。
- ampere 慢状态下只 GPU 计算就要 6.4 ms，也就是最多约 156 个/s：不超过 catalog μ 的 0.82、μ 缩放后 catalog 的 0.88；加上每个请求的 CPU 侧间隔，实际还会更低。所以 **μ = 0.93 覆盖不了这个慢状态**。
- 慢状态对 E1 的影响在两个 run 里都不大：
  - 不乘 μ 的 run 里，resnet makespan 窗口晚到 15.1%，其中 95% 在 R4。那一轮副本还处在快状态（b1 中位数 4.73–4.78 ms），晚到的原因是改 batch 时副本饱和（第 3.3 节）。慢状态的 R7–R11，makespan 窗口里 5441 个 resnet 请求只有 81 个晚到。
  - R7–R10 的 resnet 需求是 58–110 个/s，低于慢状态的约 156 个/s，所以没有积压。两个 run 在 R7–R10 都只有一个处于慢状态的 1g 副本，情况相同。
  - 能在数据中看到的影响是负载接近慢状态容量的稳态（R11 需求 147 个/s，R12 134 个/s）：不乘 μ 的 R11 稳态 resnet 晚到 876 / 4388（20%）、R12 554 / 4070（14%）；μ run 同样两轮为 294 / 4388（6.7%）、138 / 4086（3.4%）。
- 也就是说，本次没有因为慢状态而积压，是因为负载低于慢状态的容量，不是 μ 覆盖了它。

### 4.4 处理方式

- 作为测试平台的已知局限记录：ampere 上受 CPU 下发限制的小 batch 选项（resnet b1），在部分负载下推理核频率约 1.9 GHz，GPU 计算时间比 profile 慢 35–45%。这不是 SliceWise 的问题，也不是 μ 应该吸收的误差。
- 可能的修复都没有做：
  - 把推理子进程固定到单个逻辑 CPU（验证上面的推测，只改 runtime，不用重测 catalog）；
  - 在 BIOS 中改成性能模式（涉及主机设置，没有改）。

## 5. 结论

- 乘 μ = 0.93 之后，R3–R12 全部可行（R1 在 3 块 GPU 内不可行，跳过）。
- makespan 窗口：失败 0，按 profile 口径超过 SLO 0；按 SLO + router 固有延迟，晚到从 8.6% 降到 2.2%。
- 稳态：晚到从 27.6% 降到 5.5%，失败从 330 降到 0。
- 代价：R6 需要借 rtx1 部署临时副本（makespan 46.5 s），R5、R12 的目标布局各多用一块 GPU。R3、R5 因为余量足够变成 0 动作的轮次。
- 晚到的改善来自容量余量：不乘 μ 时晚到集中在实际容量低于承诺、副本饱和的轮次，乘 μ 后这些轮次基本消失；R3、R5 变成 0 动作也去掉了两个晚到最多的窗口。没有证据表明 batch 变小有单独的作用。
- ampere 上 resnet b1 的 CPU 频率问题 μ = 0.93 覆盖不了（慢状态最多只有 catalog 的 0.82），本次没有造成积压是因为这些轮次的负载低于慢状态的容量。
