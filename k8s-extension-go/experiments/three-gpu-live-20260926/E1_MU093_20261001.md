# E1 μ = 0.93 实验与分析（2026-10-01）

本文记录 μ 系数实验：规划时把 catalog 乘以 μ = 0.93，其余与最终 E1 相同，只跑 SliceWise。μ 的定义和取值依据见 `E1_FINAL_20260930.md` 第 7 节；对照组是最终 SliceWise run `20260930T154846.076040Z`（下文称"不乘 μ"）。

```
python3 live_runner_20260926.py --execute --e1 --e1-first-round 2 \
```

- **R1 跳过**：乘 0.93 后 R1 需要超过 3 块 GPU。离线扫描显示 R1 最多只能承受 0.975，这本身就是乘 μ 的一个结果。
- **R2 是初始放置**：从空集群建出 R2 布局，变换期间没有流量（source 承诺为 0），和不乘 μ 时的 R1 一样，不计入变换统计。
- 没有引入新的规划参数，μ 只作用于 catalog。

## 2. 为跑通 μ 实验做的修复

乘 μ 之后，planner 第一次在 E1 里用到 Stage 3 的临时容量（R6：借 rtx1，放一个 resnet 2g 临时副本，再对 ampere-gpu1 做 partial）。之前所有 E1 都没有走到这条路径，暴露了 executor 的两个问题：

| # | 现象 | 原因 | 修复 |
|---|---|---|---|
| 1 | R6 部署临时副本时报 `target runtime not found`（run `163828`） | planner 把临时副本列在 `summary.executionRuntimes`，executor 执行动作时只查 `desiredRuntimes`（目标状态） | 4093edb：执行动作时查目标 runtime，再加上只在 `executionRuntimes` 里的 runtime。hostPort 由 GPU 和 slot 固定算出，两份列表合并不会冲突。最终状态验证仍只对照目标 |
| 2 | R6 执行成功，但 R7 前的 preflight 发现 registry 不稳定（run `170311`） | plan 结束时 `persistFinalLogicalBindings` 按 `physical_id_map` 写 logical-binding ledger，而这个 map 也包含已经归还的借用 GPU（logical 1001 → rtx1），于是 rtx1 被记为 active 但没有 runtime | 37615f0：只为目标状态中的 GPU 写 binding。对 9/30 的 260 个 plan 回放，只有两个借了 rtx1 的 R6 plan 受影响 |
| 3 | 实验跑完，但 runner 的输出验证报 "round 3/5 has incomplete actions" | R3、R5 是 0 个动作的轮次（第 3.1 节），验证要求每轮都有 action status | runner 只在 plan 有动作时要求 action status；`e1_analyze.py` 把 0 动作的轮次写进 `makespan_window_metrics.csv`（`no_op = True`，窗口 0 s，违反率 0）。重跑验证无错误，见 `analysis/revalidation_20261001.json` |

- 两次失败后，集群都停在 R6 的状态，registry 要求修复 rtx1。每次都手动提交了一个修复 MigActionPlan（只对 rtx1：清 binding → 清 template → 归还 GPU），再清到空后重跑。
- 失败的 run `163828`、`170311` 没有提交。
- `audit_makespan_run.py --expected-rounds 11`：通过，0 错误。

## 3. 结果

### 3.1 每轮

makespan 窗口 = 第一个动作开始到最后一个动作结束。"晚到" 按 SLO + router 固有延迟判断（`E1_FINAL_20260930.md` 第 5.2 节），分母是完成的请求。

测试平台共 3 块 GPU（ampere-gpu0、ampere-gpu1、rtx1-worker-gpu0），每轮最多用 3 块。"GPU" 列是 source → target 的块数，"借"是只在变换期间用、结束前归还的 GPU。

|---|---|---|---|---|---|---|---|---|---|---|
| R2 | 36（初始放置） | 0 → 3 | 26.8 | — | — | — | 4 | 3 → 3 | 0.8 | 0.0% |
| R3 | **0** | 3 → 3 | 0 | 0 | **0** | 0 | 9 | 3 → 3 | 14.5 | 25.3% |
| R4 | 15 | 3 → 2 | 6.0 | 4403 | 0.1% | 0 | 31 | 3 → 2 | 35.8 | 10.3% |
| R5 | **0** | 2 → 2 | 0 | 0 | **0** | 0 | 33 | 2 → 1 | 34.6 | 7.5% |
| R6 | 39 | 2 → 1，借 rtx1 | 46.5 | 27874 | 3.8% | 0 | 8 | 1 → 1 | 1.1 | 77.0% |
| R7 | 5 | 1 → 1 | 10.8 | 6303 | 6.1% | 0 | 8 | 1 → 1 | 1.0 | 21.8% |
| R8 | 4 | 1 → 1 | 0.6 | 309 | 0.0% | 0 | 4 | 1 → 1 | 0.6 | 0.0% |

| R12 | 16 | 2 → 3 | 19.3 | 11742 | 2.5% | 0 | 19 | 2 → 2 | 42.4 | 0.3% |

- **R3、R5 没有动作**：乘 μ 后上一轮的布局已经能满足这两轮的需求，planner 不做任何变换。它们的 makespan 为 0，变换期间没有请求，违反率记为 0。这是乘 μ 的直接影响，计入统计。
- R6 的 makespan 从 1.1 s 变成 46.5 s：需要先借 rtx1 部署临时副本，再对 ampere-gpu1 做 partial，最后收回临时副本。
- 乘 μ 后目标布局多用 GPU 的轮次：R5（2 块，不乘 μ 时 1 块）、R12（3 块，不乘 μ 时 2 块）。R6 的目标是 1 块，但变换期间借了 rtx1（第 2 节），结束前归还。

### 3.2 合计（R3–R12）

| | 不乘 μ | μ = 0.93 |
|---|---|---|
| **makespan 窗口** | | |
| makespan 合计 | 183.7 s | 160.9 s |
| 发出请求 | 119628 | 96190 |
| 按 profile 口径超过 SLO | 0 | 0 |
| 超过 SLO + router 固有延迟 | 10291（8.6%） | **2078（2.2%）** |
| 失败 | 0 | **0** |
| **稳态窗口** | | |
| 发出请求 | 199715 | 199808 |
| 超过 SLO + router 固有延迟 | 54952（27.6%） | **11068（5.5%）** |
| 失败 | 330 | **0** |
| **整个 run（所有窗口）** | | |
| 失败 | 405 | **0**（524706 个请求全部成功，0 拒绝、0 超时） |

- 不乘 μ 的 405 个失败全部是 vgg16 被发送端 pending 上限拒绝，发生在 R5–R7：vgg16 b16 的实际容量是 catalog 的 0.955–0.965，规划余量不到这个差距，稳态积压超过上限。
- 视觉 workload 的晚到比例（makespan 窗口，两边都有变换的轮次 R4、R6–R12）：resnet 15.1% → 2.7%，vit 14.1% → 0.4%，vgg16 2.1% → 2.4%。
- LLM 每个 workload 在 makespan 窗口里只有几到二十几个请求（例如 gpt2_p64 为 7/24），比例不可靠，不下结论。

### 3.3 改善从哪里来

有两个原因，不能全部归于"容量余量"：

1. **容量余量**：每个 workload 的承诺容量按 catalog × 0.93 计算，实际容量低于 catalog 4–5% 的情况被覆盖。vgg16 不再积压，失败从 405 降为 0。
2. **选项变了**：同样的需求除以更小的 μ，planner 选出的 MIG profile 和 batch 不同（按服务的请求数统计，R3–R12）：

| workload | 不乘 μ | μ = 0.93 |
|---|---|---|
| resnet50 | 1g b1 80%，1g b4 20% | 1g b1 79%，2g b1 21% |
| vgg16 | 2g b16 57%，2g b4 18%，2g b32 14%，2g b1 10% | 3g b4 65%，2g b32 12%，2g b16 12%，3g b1 6%，4g b1 3%，2g b1 2% |
| vit_base | 1g b16 74%，1g b1 26% | 2g b1 76%，1g b1 24% |

小 batch 在 router 里凑批的等待短（vit b16 每个副本凑满一批约 260 ms），所以"SLO + router 固有延迟"口径下的晚到大幅减少。按 profile 口径（计算时间 vs SLO），两边都是 0。

### 3.4 代价

- R1 在 3 块 GPU 内不可行。
- R6 要借 rtx1 部署临时副本，makespan 46.5 s；R5、R12 的目标布局各多用一块 GPU。
- makespan 合计反而更短（160.9 s vs 183.7 s），主要是 R3、R5 不需要变换，R4 从 35.8 s 缩到 6.0 s。

### 3.5 实际容量（容量系数）

`e1_capacity_factor.py <run> catalog_newest_v3_mu093.csv`，系数 = 饱和秒内的实际容量 / μ 缩放后的 catalog：

| 样本 | 最低 | 中位数 | 最高 |
|---|---|---|---|
| 9 个副本 × 轮次 | 0.938 | 0.958 | 1.040 |

- 饱和的只有 vit（66 s）和 vgg16（6 s），resnet 在整个 run 中没有饱和过。
- 这 9 个样本全是 ampere 上的 b1 副本：vit 1g b1、vit 2g b1、vgg16 3g b1。换算到不乘 μ 的 catalog，它们只有 0.87–0.89（R3 的一个 vit 1g b1 为 0.97）。
- 也就是说，这些副本饱和的那几秒，实际容量仍低于 μ 缩放后的承诺，差 4–6%。这些秒很短，积压被排队消化，晚到比例仍然很低。原因见第 4 节。

## 4. ampere 上的 b1 受 CPU 频率限制

### 4.1 现象

同一个选项、同一个 MIG profile，ampere 上的 b1 副本有两种速度：和 profile 一样快，或者慢 30% 以上，而且在两种状态之间是跳变，不是逐渐变慢。rtx1 上没有这种现象。

每个副本每轮 GPU 计算时间（`runtimeLatencyMs`）的中位数，与 profile（该 GPU 上的 catalog 测量值）比较：

| run | 副本 | 轮次 | 中位数 | profile | 比值 |
|---|---|---|---|---|---|
| 不乘 μ | resnet ampere-gpu0 1g (6,7) | R4–R6 | 4.75–5.05 ms | 4.88 ms | 0.97–1.03 |
| | | **R7–R11** | **6.32–6.39 ms** | 4.88 ms | **1.29–1.31** |
| | | R12 | 4.97 ms | 4.88 ms | 1.02 |
| μ = 0.93 | resnet ampere-gpu0 1g (2,3) | R2–R4 | 4.86–4.94 ms | 4.88 ms | 1.00–1.01 |
| | | **R5–R6** | **6.55–6.66 ms** | 4.88 ms | **1.34–1.36** |
| | resnet ampere-gpu1 2g (0,2) | R2–R4 | 4.15–4.34 ms | 4.43 ms | 0.94–0.98 |
| | | **R5–R6** | **6.01–6.16 ms** | 4.43 ms | **1.36–1.39** |
| | resnet ampere-gpu1 1g (1,2) | **R6–R10** | **6.33–6.40 ms** | 4.84 ms | **1.31–1.32** |
| | resnet ampere-gpu0 1g (6,7) | R10 / R11 / R12 | 4.77 / 5.31 / 5.59 ms | 4.88 ms | 0.98 / 1.09 / 1.15 |
| | resnet **rtx1** 2g (0,2)（临时副本） | R6 | 4.68 ms | 4.81 ms | 0.97 |
| μ = 0.93 | vit ampere-gpu0 1g (3,4) | R2–R6 | 19.89–19.92 ms | 19.99 ms | 1.00 |
| | vit ampere-gpu1 1g (0,1) | R7–R9 | 21.04–21.34 ms | 19.99 ms | 1.05–1.07 |
| | vit ampere-gpu1 2g (2,4) | R7–R9 | 11.43–11.54 ms | 10.93 ms | 1.05–1.06 |
| | vgg16 ampere-gpu1 3g (4,7) | R8–R9 | 2.71 ms | 2.72 ms | 1.00 |

- **受影响最大的是 resnet b1**：一次计算约 4.8 ms，大部分时间花在 CPU 下发 kernel 上，所以推理进程所在 CPU 核的频率直接决定它的速度。慢的状态下是 6.0–6.7 ms，慢 31–39%。
- **vit b1 是计算密集的**（约 20 ms），GPU 计算时间在 ampere-gpu1 上只多了 5–7%。这和同卡功耗降频的幅度一致（`E1_FINAL_20260930.md` 第 7.3 节：ampere-gpu1 达到 250 W 上限时 SM 频率降低 4–7.5%）。本次 run 没有做 DCGM 采样，不能确定是哪一种原因。
- vit b1 除了 GPU 时间变长，请求之间的间隔也变长了。ampere-gpu1 1g (0,1) 在 R9 饱和时每秒完成 44.3 个，即每个请求 22.6 ms，其中 GPU 计算 21.2 ms，间隔约 1.4 ms。profile 时这个间隔只有约 0.19 ms（wall 19.99 ms vs compute 19.80 ms）。这部分是 CPU 侧的开销（HTTP / 进程间通信 / 下发），同样受核频率影响。
- vgg16 3g b1 与 profile 一致；vgg16 4g b1 比 profile 还快（2.18 ms vs 2.45 ms）。

### 4.2 CPU 频率的证据（turbostat，最终 run 期间采样）

- ampere（Dell R750xa）没有加载 cpufreq 驱动，频率由硬件按负载自己调节，操作系统设不了。基准频率 2.0 GHz。
- 最终 SliceWise run（154846，fast3 runtime）期间用 turbostat 逐秒采样。resnet 1g (6,7) 副本的推理核是 CPU 14（与超线程 70 共用一个物理核）：
  - R4–R6：该核忙碌时频率 2.65–2.76 GHz，resnet 4.8–5.05 ms；
  - R7–R11：该核只有 1.87–1.98 GHz，resnet 6.3–6.4 ms；
  - 同一时间，其他忙碌的 runtime 推理核平均 2.6–3.1 GHz。所以不是整颗 CPU 降了频，而是这一个核被压低了。
- fast2 runtime（推理子进程阻塞等待）的 run 中，核 14 在 R7–R11 为 1.72–1.97 GHz。改成忙等（fast3）之后，C6 占比降为 0，R4–R6 的频率提高了，但 R7–R11 仍在约 1.9 GHz。所以**忙等消除了 C6 唤醒延迟，但没有解决频率问题**。
- 原因推测（**未验证**）：每个 runtime 分到一个物理核的两个超线程（例如 14 和 70），而推理子进程是单线程的，可能在两个超线程之间来回迁移。每个逻辑 CPU 看上去都只有 50–70% 忙碌，硬件按逻辑 CPU 的利用率决定频率，于是不给满速。
- 本次 μ run 没有做 turbostat 采样。4.1 节里慢状态的出现时间和幅度与最终 run 一致，但没有逐秒的频率数据直接对应。

### 4.3 与 catalog 的关系

- catalog v3 在每块 GPU 上单独 profile，测量时主机上只有这一个 runtime，推理核能跑到 2 GHz 以上。ampere 上 resnet 1g b1 测到 204.8–206.6 个/s（4.84–4.88 ms）。
- catalog 取三块 GPU 中最慢的一块，resnet 1g b1 的 catalog μ 是 rtx1 的 190.19 个/s（5.26 ms），μ 缩放后是 176.88 个/s（5.65 ms）。
- ampere 慢状态下是 6.4 ms，约 156 个/s：只有 catalog μ 的 0.82，μ 缩放后 catalog 的 0.88。所以 **μ = 0.93 覆盖不了这个慢状态**。
- 不乘 μ 的 run 里，同一现象让 resnet 在 makespan 窗口晚到 15.1%。μ run 里 resnet 多分到一个 2g b1 副本，每个副本有余量，慢状态没有造成积压（resnet 在整个 run 中没有饱和），晚到 2.7%，稳态 2.8%，没有失败。这是余量碰巧够，不是 μ 覆盖了慢状态。

### 4.4 处理方式

- 作为测试平台的已知局限记录：ampere 上受 CPU 下发限制的小 batch 选项（resnet b1），在部分负载下推理核频率约 1.9 GHz，比 profile 时慢 30–39%。这不是 SliceWise 的问题，也不是 μ 应该吸收的误差。
- 可能的修复都没有做：
  - 把推理子进程固定到单个逻辑 CPU（验证上面的推测，只改 runtime，不用重测 catalog）；
  - 在 BIOS 中改成性能模式（涉及主机设置，没有改）。

## 5. 结论

- 乘 μ = 0.93 之后，R3–R12 全部可行（R1 在 3 块 GPU 内不可行，跳过）。
- makespan 窗口：失败 0，按 profile 口径超过 SLO 0；按 SLO + router 固有延迟，晚到从 8.6% 降到 2.2%。
- 稳态：晚到从 27.6% 降到 5.5%，失败从 330 降到 0。
- 代价：R6 需要借 rtx1 部署临时副本（makespan 46.5 s），R5、R12 的目标布局各多用一块 GPU。R3、R5 因为余量足够变成 0 动作的轮次。
- 晚到的改善一部分来自容量余量，一部分来自 planner 选了更小的 batch。
- ampere 上 b1 的 CPU 频率问题 μ = 0.93 覆盖不了（慢状态只有 catalog 的 0.82），本次没有造成积压是因为余量够。
